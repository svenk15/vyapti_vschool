# VS database design — VSchool v4.3

This is the connected physical database contract. The Bible owns product and architecture rules; module DESIGN.md files own column schemas, responsibilities and named transaction workflows. TABLE_REGISTRY.json is a checked catalog derived from those LLDs, not a second independent design. Local PostgreSQL checkpoints include the Academics-owned Teacher table; Students-owned Student, Enrollment and SectionPlacement tables; and AttendanceSession after their forward migrations. Other Attendance tables remain planned. Migration status is physical state only and does not claim task verification or human acceptance.

## Naming decision — DB-ADR-001

Use **`vs_`**, the user-selected abbreviation of VSchool, as a stable storage namespace. Physical tables are singular lowercase snake_case: `vs_<module>_<entity>`. Columns are lowercase snake_case. Preserve logical PascalCase model names and camelCase properties through Prisma `@@map` and `@map`; repositories hide persistence names from the domain. Namespace denotes ownership, not authorization.

| Object | Convention | Example |
|---|---|---|
| Table | vs + owner + singular entity | `vs_attendance_session` |
| Column / foreign reference | snake_case / referenced concept + _id | `organization_id`, `school_id`, `student_id` |
| Primary key | table + _pkey | `vs_platform_setup_check_pkey` |
| Unique / FK / index | table + short purpose + _key / _fkey / _idx | `vs_students_student_admission_key` |
| CHECK / exclusion constraint | table + purpose + _check / _excl | `vs_attendance_session_time_check` |
| Trigger / policy | table + purpose + _trg / _policy | `vs_platform_audit_entry_append_only_trg` |
| Native enum, if explicitly chosen | vs + owner + concept + _enum | `vs_attendance_status_enum` |
| Migration directory | UTC timestamp + reviewed intent | `20261003000300_vs_prefix` |

Identifiers must fit PostgreSQL's 63-byte default limit, use ASCII `[a-z][a-z0-9_]*`, and stay unique after shortening. Use a reviewed concise purpose; for unavoidable collisions, preserve the suffix and append eight hex characters of SHA-256 of the full proposed name. Store the final explicit constraint/index name in Prisma `map` or migration SQL. Do not rely on silent truncation. No plural/singular mixture, customer-name tables, per-tenant suffixes or abbreviations invented by a module author. Keep `school_id` for branch scope to match the existing domain; do not add a competing branch_id pointing to the same concept.

Prisma's `_prisma_migrations` is a framework-owned exception. Extension/provider objects are explicit external exceptions, never an excuse to exempt business tables. The original applied migration's historical PascalCase name is retained so its checksum stays valid; the forward migration produces the current naming convention.

## Database/schema and tenant boundaries — DB-ADR-002

The initial deployment uses one PostgreSQL database and the `public` SQL schema. Modules own table prefixes and repository ports rather than separate SQL schemas. `organization_id` identifies the institution tenant. `school_id` identifies its branch; optional `campus_id` is a subordinate physical site. Separate institutions can never share an operational row. Branch-owned tables store both identifiers; composite unique keys and FKs include both. Person is institution-scoped; login identity is global; neither makes pupil records globally readable.

Institution control-plane tables have organization scope. Brand defaults have nullable school scope with explicit partial uniqueness and same-owner reference checks. The SetupCheck marker is deployment-scoped. RLS, restricted runtime roles and transaction-local verified scope remain required TEN-03 production work; a prefix and a scoped WHERE clause alone do not prove isolation. Exports, jobs, file paths, caches, logs and notification recipients must carry the same verified scope. Institution administrator permissions do not imply branch pupil/finance/health access.

Under the temporary Path A development exception in TEN-ADR-006, every future tenant-owned or identity/security table migration must record its tenancy class, scope/owner columns, composite constraints, indexes, intended RLS policy and TEN-03 closure gate in its LLD and TABLE_REGISTRY.json. Database enforcement, ENABLE/FORCE, role grants and restricted-role SQL tests are deferred to TEN-03; application authorization and scoped data access remain mandatory now. Do not retrofit existing tables ad hoc. No multi-client production release before TEN-03 proves enforcement. See [TEN-ADR-006](modules/tenancy/DESIGN.md#rls-and-release-verification).

## Column schema rules

Every field in a module data table is required unless explicitly nullable. Business IDs and FKs are `uuid`, generated by the application IdGenerator; they have no implicit database default. The setup marker's ID is `text`. Instants use `timestamptz(3)`, civil dates use `date`, revisions/counters use `integer`, and money in later finance design uses an exact integer-minor-unit or reviewed decimal contract plus currency, never floating point. Field length bounds shown as varchar/char are enforced physically. CamelCase names in workflow prose map mechanically to snake_case.

State fields written as allowed labels without an explicit type mean constrained `varchar(20)` with the listed values; role codes use `varchar(40)`, and import state uses its explicit width. Do not implement unrestricted text states. Native enum adoption needs a reviewed migration decision. Root version is positive and starts at 1; owned children/revisions use their explicitly named revision, not a fabricated competing aggregate version. A field has no database default unless listed; application commands supply required clock/version/boolean/status values. `created_at` is not automatically an updated_at contract. Publication/revision history is immutable.

JSONB is limited to typed versioned envelopes, configuration limits, safe audit differences, import normalization or immutable snapshots. IDs needed for relational joins stay constrained columns. Module/task design defines each payload shape and hash normalization. JSON does not replace foreign keys or a permission matrix. Distinguish NULL (absent/not applicable) from empty data.

## Join contracts that power the experience

Read queries are scoped and authorized before data is returned. The examples below are planned SQL read shapes, not SQL to run against this starter: their business tables do not exist yet. Parameters come from the verified actor/context, not direct trust in URL/body tenant IDs. CROSS-module reads are implemented through owner-approved projections/facades; raw physical joins live in infrastructure. Every SELECT lists safe output fields rather than SELECT *.

### Authorized branch switcher

Account status is verified first. Membership enumerates operational branches; institution grants enumerate separately authorized configuration metadata. Do not join an institution grant into a pupil-data permission.

```sql
SELECT s.id, s.name, o.id AS institution_id, o.name AS institution_name
FROM vs_access_school_membership AS m
JOIN vs_access_school AS s
  ON s.organization_id = m.organization_id AND s.id = m.school_id
JOIN vs_access_organization AS o ON o.id = s.organization_id
WHERE m.account_id = $1 AND m.status = 'ACTIVE'
  AND s.status = 'ACTIVE' AND o.status = 'ACTIVE'
ORDER BY o.id, s.id;
```

Context switching verifies the exact candidate branch again, then clears protected drafts/caches. The switcher query is not a permanent grant cached in a session token.

### Open/submitted attendance roster

The application verifies the current account/membership, effective Attendance module and dated teaching assignment or admin read permission before this query. A frozen roster supplies historical name/roll; the current record is a projection. Scope appears in every child join. NULL attendance on an OPEN roster is unmarked, never ABSENT.

```sql
SELECT r.student_id, r.display_name_snapshot, r.roll_number_snapshot,
       a.status, a.late_minutes, a.current_revision
FROM vs_attendance_session_roster_entry AS r
JOIN vs_attendance_session AS s
  ON s.organization_id = r.organization_id AND s.school_id = r.school_id
 AND s.id = r.session_id
LEFT JOIN vs_attendance_record AS a
  ON a.organization_id = r.organization_id AND a.school_id = r.school_id
 AND a.session_id = r.session_id AND a.student_id = r.student_id
WHERE r.organization_id = $1 AND r.school_id = $2 AND r.session_id = $3
ORDER BY r.roll_number_snapshot NULLS LAST, r.student_id;
```

When the entity begins with its exact owner name, do not repeat it: AttendanceSession in Attendance maps to vs_attendance_session. Other physical names are explicit in the catalog; authors do not invent aliases locally.

### Module configuration

Read OrganizationEntitlement for the exact institution, LEFT JOIN BranchActivation on organization_id + module_id + selected school_id, then combine deployed manifest/release availability and current actor/resource permissions. Missing activation is disabled. Dependencies must be licensed and active. Fee obligations block unsafe removal when Finance is implemented; there is no cross-module DELETE cascade to simulate disabling a capability. Disabled navigation is derived from this server result; writes repeat the gates under transaction guards.

### School-branded public login

Resolve an exact public_slug or verified hostname. Select a published institution default or explicit branch override, join current_revision_id to the same profile's published revision, and join only approved assets with matching organization/school ownership. A NULL branch scope requires explicit IS NOT DISTINCT FROM comparisons or type-specific checks; a nullable FK alone does not prove same owner. Unknown/unpublished identity returns safe 404. The response allowlist contains public names/palette/welcome/approved logo/support/locale, never credentials, drafts, membership or module entitlements. Authentication subsequently verifies the user's school access independently.

## Write workflows and transaction responsibilities

| User flow | Database reads | Atomic writes / outcome |
|---|---|---|
| Provision school | Current operator authority and duplicate institution/school/login constraints | Access roots + membership/grant + platform audit/outbox; no partial school on conflict |
| Configure branch modules | Account, institution/branch guards, entitlement/activation versions, dependency/obligation facades | BranchActivation + ConfigurationChange + revision + receipt + TenantOutbox; all or none |
| Register/enroll student | Verified branch permission, Person reference, year/section and dated range constraints | People owner facade + Student/Enrollment/SectionPlacement as required + envelopes; no cross-owner direct writes |
| Open attendance | Current actor/assignment, session/calendar, dated enrollment/placement | Frozen roster + OPEN session/version + audit/outbox/receipt; no AttendanceRecord before submit |
| Submit attendance | Exact frozen roster/version, every required status, current entitlement and teaching authority | All current records + immutable submit revision + SUBMITTED session + envelopes in one commit |
| Correct attendance | Submitted session/version, current correction permission and reason | Current projection + immutable correction revision + version + envelopes; original history retained |
| Confirm CSV import | Job preview/version, row hash and external student mapping | Each accepted row enlists owner creation and SourceStudentMap with row result; resumable job avoids duplicate pupils |
| Publish branding | Current authority, profile version, approved safe assets and palette | New immutable published revision + pointer + transactional audit/outbox/receipt; public identity JSON is no-store and image URLs are content-hash immutable, so no mutable cache invalidation is needed |
| Export scoped report | Effective module and export permission, current scoped sessions/records/revisions | ExportRun and safe download result; no stored competing attendance totals or permanent public files |
| Save weekly timetable pattern | Current actor, branch/year, Timetable/Academics/Staff module eligibility, current draft version | One versioned branch/year draft plus ordered lesson/break periods, School revision and evidence/receipt; no publication or session generation |

Commands lock actor account rows → Organization guard → School guard in the documented order. Business commands take Organization FOR SHARE; configuration commands take FOR UPDATE. Scoped aggregates/version checks and receipt replay follow current authorization. Audit/outbox/receipt failures roll back business writes. Network side effects occur after commit through durable outbox consumers. Concurrency/deadlock behavior is verified with real PostgreSQL, not mocked repositories alone.

## Migration and takeover runbook — DB-ADR-003

1. Read Bible, module DESIGN/TASKS/CURRENT_STATE, catalog and actual prisma/schema.prisma. Planned tables and installed tables are different evidence.
2. Define each column, FK target, uniqueness, indexes, checks/RLS and upgrade/backfill in the named module design before migration.
3. Map every model/table and camelCase column explicitly; use reviewed SQL where Prisma cannot express a required constraint.
4. Add a new timestamped forward migration. Never rewrite an already-applied migration or use reset/db push to bypass the history.
5. Rehearse both a clean database and an existing baseline containing synthetic rows. Prove row IDs/timestamps/history survive an upgrade, ORM and SQL agree, and rerunning deploy changes nothing.
6. Record actual migration IDs, tests, source fingerprint/commit, demo URL and owner feedback in the module CURRENT_STATE. Rollback of application code after a schema change needs compatibility analysis; do not assume old binaries still understand renamed objects.

Every new tenant-owned or identity/security table migration must record its table class, exact scope columns, constraints, supporting indexes, intended policy, owner and TEN-03 closure gate in the owning LLD and `TABLE_REGISTRY.json`. During the explicit TEN-ADR-006 Path A development exception, the same forward migration adds a table comment documenting deferred enforcement; `pnpm check:db-design` enforces that annotation. After TEN-03 turns on enforcement, each new tenant table migration must ENABLE and FORCE RLS and create its policy in that same migration. Global operator and deployment-only tables require their recorded exception and narrow access path. Never change an applied migration to retrofit these rules.

The current rename migration transaction renames the previously released vora_platform_setup_check and its PK to vs_ names without DROP/CREATE or copying/deleting rows. Stop the previous local server before migrating, regenerate Prisma, then restart the matching code. Health API behavior stays unchanged. A stopped older starter would otherwise look for the old physical table. No business-table schema is migrated by this change.
