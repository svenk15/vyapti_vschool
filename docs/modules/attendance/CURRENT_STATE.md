## ATT-03 design readiness — 5 October 2026

ATT-02 is VERIFIED/PENDING; its only dependency is implementation-level, with no human-PASSED gate. Existing `AttendanceRecord`, immutable `AttendanceRevision`, session version and scoped receipt/evidence tables already support correction; ATT-03 should add no table or migration unless implementation proves a missing invariant. Current correction capability is `attendance.correct`, and only current School administrators receive it; teacher `attendance.read_class` remains read-only. Correction and history reads must still recheck current account/token, active membership, branch activation, `attendance` plus dependency entitlements, and resource scope. Admin correction additionally requires active `attendance.correct`; history uses the same current authorized school-read boundary as existing detail (`attendance.read_school` for school-wide admin history), never a client-supplied tenant ID.

Resolved write contract: acquire account → Organization → School → AttendanceSession locks; after authorization re-read session, frozen roster and current records under the transaction. Require SUBMITTED, expected session version, nonempty subset of unique frozen student IDs, meaningful actual status/late-minute change and a trimmed 5–500 character reason. `late_minutes` remains 1–480 only for LATE; other statuses store NULL. Update only named AttendanceRecords and their `current_revision`, append one `CORRECT` revision with the next session revision number, increment session version, and write audit/outbox/receipt atomically. Stable same-key/same-canonical-command retry returns the original result only after fresh current authorization; changed payload conflicts. `UNIQUE(scope,session_id,number)`, roster/session composite references and immutable revision trigger remain authoritative. Concurrent corrections serialize on the session and stale expected versions fail without a partial write. Reads stay lock-free and return history ordered by revision number; after branch authorization actor labels resolve through AccountPersonBinding→Person, with unbound administrators labeled “School administrator”. Preserve student IDs and from/to statuses in owned revision history, but exclude display names, roll values and raw student PII from audit/outbox/receipt payloads.

Resolved transport/UI contract: admin `POST /api/v1/sessions/:id/corrections` accepts `{expectedVersion,changes:[{studentId,status,lateMinutes?}],reason,key}` and admin `GET /api/v1/sessions/:id/history` returns scoped immutable revisions, safe actor display names and times. A submitted-session list leads to an admin review workspace. Show current and prior values, reason, author/time and corrected state; ordinary assigned teachers see the read-only submitted result and cannot call the correction route. Errors: teacher/unauthorized→403 or resource-safe 404; missing/invalid reason or input→422; stale version, session not SUBMITTED, duplicate/no-op/out-of-roster change→409; foreign session→404; database/evidence failure→503 and total rollback. UI preserves correction input for validation/stale retries, while same-key replay is unchanged.

Physical/query contract: no schema change is expected. Scoped session lookup uses `(organization_id,school_id,id)`; history filters by the same scope/session and orders by `number` using `vs_attendance_revision_number_key`; current-value join uses the frozen `(organization_id,school_id,session_id,student_id)` key between records and roster entries. After branch authorization, actor labels resolve through AccountPersonBinding→Person; an unbound administrator receives the generic “School administrator” label. No email is returned. Run `EXPLAIN (ANALYZE, BUFFERS)` for scoped history and the roster/current-record join; report actual synthetic counts, indexes and plans without treating small test data as the Bible pilot or TEN-03 scale gate. Path A BRANCH classification and TEN-03 closure remain unchanged; application authorization remains enforced.

Verification contract: unit correction diff/reason/late policy; real PostgreSQL atomic update+revision+receipt, rollback after evidence failure, two concurrent correction commands with one stale-version rejection, immutable revision trigger, same-key replay and current permission/foreign-scope checks; browser admin correction from absent to excused with visible history, and assigned teacher read-only/direct-action denial on desktop/mobile.
