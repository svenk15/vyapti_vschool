# Institution, branch and module configuration — design

Phase 1 · Revision 1 · 3 October 2026. Runtime implementation limits are explicit in CURRENT_STATE.md.

## Database naming and physical mapping

All physical objects follow [the VS database contract](../../DATABASE_DESIGN.md). Table names and columns below are physical SQL names; workflow prose uses logical domain names. `organizationId` maps to `organization_id`, `schoolId` to `school_id`, and `scope` expands to both columns. Models retain PascalCase through Prisma `@@map`; camelCase fields use `@map`. Planned schemas are implemented only through their named tasks and reviewed migrations.

## Ownership and aggregate boundaries

Access retains Organization, School and memberships; Tenancy owns OrganizationEntitlement and BranchActivation configuration. Do not duplicate institution identity in a competing Tenant table. InstitutionGrant is Access-owned. TenantDirectory is a future deployment-routing port, not a business data source. `ModuleManifest`, `ModuleId`, `DependencyClosure`, `ConfigurationRevision` and `BranchScope` are immutable values. Current code implements a pure subset in backend/modules/tenancy/domain/entitlements.ts.

TEN-ADR-001: institution entitlement and branch activation are separate roots; effective access intersects release availability + entitlement + activation + current user/resource permission. Alternative: menu-only toggles rejected. Tests include direct endpoint denial and queued work after disable.

TEN-ADR-002: shared PostgreSQL with composite constraints, scoped repositories and production RLS defense. Dedicated tenant DBs are a later routing option. No per-client code fork.

TEN-ADR-003: configuration metadata changes use actor account locks → Organization guard → School guards in sorted order. Ordinary business commands take Organization FOR SHARE after account locks and before School FOR UPDATE; institution entitlement/config changes use Organization FOR UPDATE. Global account changes take all affected Organization/School guards in sorted order. This extends CORE-005 and prevents disable racing a command with cached entitlement. No acquiring an account lock after a scope lock.

TEN-ADR-005: Tenancy owns per-institution Access trust-mode configuration and its versioned history; Access owns UserAccount, invitations, password-reset tokens and security facts. The database Organization root remains Access-owned and has a conservative OPERATOR_CLI default; the application explicitly selects HYBRID only when creating a new institution after IAM-04. A platform operator alone changes trust mode; an institution administrator cannot change recovery/provisioning channels. The typed Access invalidation application port is enlisted by Tenancy in the same unit of work, so ConfigurationChange and token revocation cannot commit separately. See Access IAM-ADR-008 for modes, table contracts, recovery policy and lock ordering.

## Read joins and authorization

Institution selector: current Account → active InstitutionGrant or active SchoolMembership → active Organization, DISTINCT institution IDs. Branch selector: current account's explicit active SchoolMembership → School → Organization; institution admin sees manageable branch metadata via branch.manage, not pupil records. Granting self operational access is a separately audited action allowed only within delegated policy. Overview contains configuration/health summaries only unless explicit report capability and branch grant set are supplied.

Entitlement view: OrganizationEntitlement LEFT JOIN BranchActivation on organizationId/moduleId and selected school, combined with a server-owned immutable deployed release catalog. Return `{moduleId,licensedState,activationState,releaseAvailable,effective,dependencies,blockingReasons,version}`; clients cannot mutate entitlement or claim a release by posting this DTO. The Phase 1 demo explicitly releases `student_core`, `academic_core`, `staff_core` and `attendance`; later product modules remain release-unavailable. Contracted entitlement is still recordable, but activation confirmation for an unavailable release returns `409 RELEASE_UNAVAILABLE`; no menu or protected command is enabled. Tests supply an immutable release manifest for the intended case. User menus use server-produced effective capabilities and are re-evaluated on context switch.

**SA-COMP-09 / SA-08 contract (10 October 2026):** the owner authorized an immutable, non-binding capability-interest submission. A current active `SCHOOL_ADMIN` may submit exactly Attendance, Family portal, Fees & payments or Transport plus a normalized 5–1000 character need. It creates no purchase, payment obligation, entitlement, activation or release change. An active institution administrator who also has the branch context needed to enter the operational portal sees recent institution submissions; other school administrators see only their current branch. Review decisions, cancellation, withdrawal and automatic resubmission remain outside this slice, so the stored state is only `SUBMITTED`. A new key records a distinct expression; exact same-key/same-input replay returns the original record, while same-key/different-input conflicts. The receipt stores only the request ID and the outbox excludes the free-text need.

The read joins current Account → active branch SchoolMembership/SCHOOL_ADMIN → active School/Organization, then OrganizationEntitlement LEFT JOIN current BranchActivation for status. CapabilityInterest history filters `(organization_id,school_id)` for branch users or `organization_id` after a current `INSTITUTION_ADMIN` grant check. Submission locks Account UPDATE → Organization SHARE → School SHARE, repeats all active-scope checks, writes CapabilityInterest, the minimal TenantCommandReceipt and a PII-free `CapabilityInterestSubmitted.v1` outbox record atomically. Revocation or a wrong branch returns a scoped denial and writes nothing. Reads do not take mutation locks.

Playwright covers school-admin submission and institution inbox at desktop/mobile widths, including keyboard-reachable fields and explicit non-binding copy. ## Transport and state transitions

POST /api/v1/institutions/:id/branches requires institution branch.manage, input `{code,name,timezone,key}`; result safe branch metadata. POST /api/v1/context/switch accepts candidate institutionId/branchId, validates membership and returns new actor context; no trusting prior UI selection. Reads/commands use explicit scope rather than a mutable global server singleton.

POST /api/v1/branches/:id/modules/preview accepts desired module IDs, returns required foundations/dependents/obligations/blockers and pinned institution/branch config revisions. POST .../confirm binds desired state+preview hash+expected root/config versions+reason/key. A verified platform operator's trusted CLI records institution contracts; an active institution admin with `module.configure` previews/confirms activation only within an already operationally granted branch. Neither authority implies the other. Unknown module→422; unlicensed, dependency-disabled or release-unavailable→409; revoked authority→403; foreign branch→404; stale preview→409; malformed or unknown limits→422. A denied confirmation writes no configuration change, receipt or outbox. A successful contract/activation updates the appropriate configuration revision and root version, and persists ConfigurationChange, TenantCommandReceipt and TenantOutbox in the same transaction; exact replay is reauthorized, input-hash checked and returns the original response. Fees obligations use a FinanceEligibility port; until Finance ships, releaseAvailable=false and no fake successful activation.

## RLS and release verification

RLS is a mandatory defense-in-depth release gate, not currently installed. TEN-03 remains the consolidated implementation and verification task. TEN-ADR-006 explicitly selects Path A for the current development sequence: record every affected table’s classification, scope columns, constraints, indexes and intended policy now; defer database policy enforcement and runtime-role changes to TEN-03. This temporary development exception is not production authorization. No multi-client production release is allowed until TEN-03 enforcement and restricted-role verification pass.

### TEN-ADR-006 — RLS compatibility contract (4 October 2026)

**Inventory and current roles (read-only table state, 6 October 2026; later role setup is recorded in CURRENT_STATE).** Configured development and test connections are `vyapti_vschool` and `vyapti_vschool_test`. Each is LOGIN, NOSUPERUSER, NOBYPASSRLS, NOCREATEDB and NOCREATEROLE, but both own their database and all 52 ordinary relations in `public`, and each can create in `public`; object ownership bypasses RLS unless `FORCE ROW LEVEL SECURITY` is enabled. Both catalogs report zero RLS-enabled tables and zero policies. The local PostgreSQL cluster also has `venky` and `vschool` LOGIN superusers; neither is used by the configured application connections. Existing `schoolos_starter*`, demo and fresh-dev login roles have no current public-table DML grants and are not configured runtime roles. Separate `vyapti_vschool_runtime` and `vyapti_vschool_test_runtime` roles now exist; each is NOSUPERUSER, NOBYPASSRLS, NOINHERIT, owns no database/table and has no table DML or public CREATE. Both databases have 26 current migrations and no pending files; the test `_prisma_migrations` ledger retains 28 rows, 26 applied and two rolled-back. Credentials are not recorded. TEN-03 preserves current owner identities for migration compatibility and does not treat owner sessions as runtime isolation evidence. This catalog snapshot is local-only; provider roles remain uninspected.

**Table classes.** Each new physical business table must declare one class in its owning LLD and migration review: (A) branch operational, with non-null `organization_id` + `school_id`; (B) institution control-plane, with `organization_id` and optional same-institution `school_id`; (C) global identity/security, keyed by `account_id` or global identifier and not made tenant-readable by a client-supplied tenant; or (D) deployment/public sanitized data with deliberately narrow access. The deployment-scoped setup marker and Prisma migration ledger are infrastructure exceptions, not business tenant tables. TEN-03 will inventory every migrated table and record owner, class, tenant key, policy, role grants, FORCE status and supporting indexes in a checked policy registry. Class D may use a sanitized view/function with fixed output rather than base-table grants.

**Roles and ownership.** Separate `vschool_migrator` (NOLOGIN in production or credentialed only in migration automation; owns schema/tables and may bypass policies only during controlled migration) from `vschool_runtime` (LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, NOBYPASSRLS, no object ownership, no schema CREATE, only required DML/sequence/function grants). Use distinct local/dev/test role names and credentials; migrations run as owner and the application pool connects only as restricted runtime. Runtime cannot SET ROLE to owner, alter policies, disable triggers/RLS, or access arbitrary files. The actual provider/local database privilege model must be proven rather than assumed. Every protected table uses ENABLE and FORCE ROW LEVEL SECURITY unless the TEN-03 exception register documents why a policy/view boundary is safer and tests that path. Neither table owner nor superuser sessions count as isolation evidence.

**Transaction context and authenticity gate.** Each branch transaction calls `vs_set_verified_branch_context(account_id, token_version, organization_id, school_id)` on its checked-out transaction before any branch business query. The current fixed SECURITY DEFINER helper validates active account/token version, organization, branch and membership, then sets transaction-local GUC values. It uses a pinned `pg_catalog` search path, fully qualified tables, no dynamic SQL, and EXECUTE is granted only to restricted runtime roles. However, PostgreSQL custom GUCs are caller-settable: a caller with runtime SQL access can replace these values after the helper runs. Therefore the current GUCs are not an authenticated identity proof, and **no RLS policy may trust them yet**. TEN-03 must add and verify a non-forgeable transaction binding (e.g. a narrowly owned signing secret and transaction-bound MAC, inaccessible to runtime), and every policy predicate must validate it. Tests must demonstrate that direct attempts to set account/organization/branch context cannot read or write another tenant.

Account-only Access entry uses `vs_find_account_context_by_email(normalized_email)` for one exact normalized address and `vs_set_verified_account_context(account_id, token_version)` for a known account; recovery and invitation helpers use exact token/record identifiers. These bootstrap values do not authorize tenant or resource access. Every application use case still rechecks current membership/resource permissions, entitlement, branch activation and operation rules. No request JSON, headers, cookies or job input is trusted as authorization. All scoped queries/writes remain on the same transaction/connection; commit/rollback clears context, and session-level `SET` is prohibited. Operator, audit and public-brand paths stay separate narrow exceptions, never a global bypass. Background workers establish scoped context inside their own transaction. Cross-branch reports explicitly enumerate currently authorized school IDs. No policies are enabled yet.

**Read and write policies.** Branch operational tables require row `organization_id` and `school_id` to match context that first passes the non-forgeable verifier above, plus current active membership; application resource permission remains required. `USING` protects SELECT/UPDATE/DELETE and `WITH CHECK` protects INSERT/UPDATE, including both old and new row scope. Institution control-plane policies bind `organization_id` to verified institution context; nullable branch rows must be either genuinely institution-wide or match an allowed branch, according to table contract. Membership/grant resolution cannot recursively depend on a policy that itself needs that membership: use a narrowly reviewed security-definer predicate with pinned `search_path`, no caller-controlled dynamic SQL, restricted EXECUTE, and tests, or perform a trusted prevalidated transaction context lookup through a separate non-RLS authorization path. RLS supplements, and never replaces, current resource permissions or scoped composite FKs.

**Global identity and privileged exceptions.** `vs_access_user_account` is global login identity: ordinary runtime paths may read/update only the authenticated account's own credential/session fields through Access use cases, not scan identities by tenant. Account-wide password recovery is a named Access workflow that may locate an exact normalized address and lock/update that one global account; rate limits, verified address, trust policy, token hash, token consume/revoke, tokenVersion/session revocation and security evidence remain in the same guarded application transaction. Do not grant generic tenant roles broad UserAccount or `vs_access_password_reset_token` access. Invitation acceptance is similarly a narrowly named token capability bound to exact recipient/scope and atomically rechecks current policy. Operator CLI workflows use a separate verified operator connection/factory with explicit command allowlist and immutable evidence; never enable a global RLS bypass flag on the web pool. Audit/security evidence is append-only: scoped actors read only authorized scope; platform audit review uses a separate audited operator read path returning redacted DTOs. Migration owner, emergency operator and sanitized public-brand paths are explicit exceptions, each least-privileged and separately tested. No exception may silently permit tenant table DML from the app runtime.

**Index contract.** Every tenant policy lookup must be supported by indexes reviewed with its read/write mix: branch data starts with `(organization_id, school_id, ...)`; institution history by `(organization_id, occurred_at/id)`; account membership/grant probes by `(account_id, status, organization_id, school_id)` as applicable; recovery by unique normalized email and token hash/expiry-state indexes; append-only audit by `(organization_id, occurred_at, id)` with a separate actor index where operator investigations need it. Avoid duplicating an existing leading-column index. Policy helper joins must use matching composite keys and bounded indexed lookups. TEN-03 records EXPLAIN/ANALYZE plans for representative queries and write amplification before accepting additional indexes.

**Every future migration under Path A.** Any migration that creates a tenant-owned or identity/security table must, in the same forward migration and LLD, (1) classify it and add required scope/owner columns and scoped composite keys, (2) record supporting constraints/indexes and the intended policy in TABLE_REGISTRY.json, (3) mark database enforcement `DEFERRED_TEN_03` with the table owner and closure gate, and (4) test existing application authorization and scoped persistence. Do not add ENABLE/FORCE RLS, policy helpers, restricted-role grants or transaction-local DB settings before the TEN-03 compatibility implementation. This is the explicit temporary development exception: new tables may be used under the current development role while remaining application-authorized and scoped; they are not database-isolated against arbitrary SQL. TEN-03 owns policy objects, role grants, restricted-role tests and retrofit of all registered tables. No multi-client production release before that gate passes.

The database-design check enforces this migration rule for new tenant tables: a newly registered table must provide a class, exact scope columns, intended policy, owner and TEN-03 closure gate. Once TEN-03 enforcement is enabled in `TABLE_REGISTRY.json`, a new migration must also enable and force RLS and define its policy in the same migration. Historical migrations remain immutable; the TEN-03 forward migration supplies policies for already-registered tables.

## Physical configuration revision and typed limits

Access-owned Organization and School contain configuration_version integer default 1, positive. Institution contract changes compare/increment Organization.configuration_version; branch activation changes compare/increment School.configuration_version. Preview pins both institution and branch revisions; confirmation rejects a changed entitlement revision even if the branch revision is unchanged. ConfigurationChange.expected_revision/new_revision records the guard revision for its institution/branch target. Individual entitlement/activation version remains that root’s optimistic version. Revisions and immutable receipt/audit/outbox commit together. Module limits use manifest_version plus a validated module-specific JSON shape (allowed quota keys only, nonnegative bounded integers, no arbitrary tenant SQL or feature code).

BrandProfile public_slug is globally unique lowercase [a-z0-9] plus internal hyphens, 3–80 characters, exact lookup; publication never enumerates private memberships. Brand owner-null scope comparisons require IS NOT DISTINCT FROM or equivalent reviewed guards, not a nullable foreign key shortcut.

Until a released module defines a typed quota shape, `limits` accepts only the empty JSON object. Unknown/free-form keys are rejected; TEN-02 does not store tenant SQL or feature flags in this column.

Trust mode is not an entitlement, capability, membership or branch grant. `setTrustMode` is a platform-operator application command with organization ID, expected configuration revision, stable idempotency key, non-sensitive reason and valid in-organization audit anchor. Same-mode input is a no-op. Actual transition increments Organization configuration/root version and atomically appends ConfigurationChange, TenantCommandReceipt and TenantOutbox while the Access owner port invalidates only email tokens affected by a transition to OPERATOR_CLI. Access performs the required all-issuer/token-account joins; Tenancy never queries or writes Access token tables. Returning to HYBRID/EMAIL never restores revoked tokens. Configuration history records principalKind=OPERATOR plus operator ID and an audit-anchor account ID, without impersonating that account.

IAM-04's reserved cross-institution recovery advisory transaction guard is acquired before account/org/school row locks by trust-mode transition and all Access operations that change applicable recovery-policy access. Tenancy's operator `setEntitlement` transaction continues to take account → Organization FOR UPDATE; it does not affect the recovery access predicate. A trust transition and contract mutation still serialize on the Organization row/configuration revision. The Access port receives Tenancy's active unit-of-work context and returns only invalidated token/account IDs and a correlation reference for bounded configuration evidence.
