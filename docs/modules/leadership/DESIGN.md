# Principal leadership — low-level design

Status: active first-release design · 16 October 2026.

## LDR-01 / LEA-01 design delta

The Access module owns Principal identity and branch membership. `PRINCIPAL` is a fixed `RoleGrant` code on an active `SchoolMembership`; it is not an operator, institution administrator, school administrator, or teacher alias. Only the existing verified operator `SetBranchMembership` command may add or remove this code in the first release. School staff-management commands reject any target membership containing `PRINCIPAL`, preventing self-grant, delegated grant, suspension, role replacement, or privilege expansion through the administrator UI.

`getLeadershipHome(identity, schoolId?)` is a transport-neutral Access query. It validates the live account/token version, active organization, active school, active exact membership, and exact Principal grant in one repeatable-read scope snapshot. The optional school ID is only a candidate. It returns the existing browser-safe `AdminHome` context with `leadership.read` and `self.read`; the Principal role grants no attendance, student, staff, finance, assessment, communication, export, or mutation capability.

The context directory returns each currently authorized branch and its server-derived fixed roles. `/choose-workspace` expands these facts into distinct role/branch choices. Confirmation calls the existing context-switch endpoint, which reauthorizes the branch before setting the account-bound candidate cookie. `/leadership` then independently calls `getLeadershipHome`; revoked or forged context returns no protected content. Branch changes clear the page through a full navigation and the existing cross-tab context notification.

The Principal shell uses the shared portal shell, school branding, mobile focus trap, branch control, account entry, and separate sign-out. The initial home intentionally contains no operational totals. It states that owner projections are unavailable rather than displaying fabricated zeroes. LDR-02 will add the bounded Attendance due-register projection only after its metric contract and module/capability gate are implemented.

### Persistence and migration

No new table is introduced. Forward migration `20261016000100_principal_branch_role` replaces only the `vs_access_role_grant_state_check` constraint so `code` accepts `SCHOOL_ADMIN`, `TEACHER`, or `PRINCIPAL`. Existing rows and indexes are unchanged. RoleGrant remains a branch-classified Access table with `(organization_id, school_id, membership_id)` scope and the existing unique key. Application authorization remains mandatory; TEN-03 still owns restricted runtime roles and RLS enforcement.

### Transactions and concurrency

Principal grant changes reuse the operator-only `SetBranchMembership` transaction, account/organization/school locks, expected membership version, idempotency key, redacted audit/outbox/receipt evidence, and retry policy. Reads do not acquire write locks. A stale or revoked grant fails on the next protected read. Administrator membership commands check for `PRINCIPAL` after locking and return `FORBIDDEN` without changing grants or evidence.

### Failure states and verification

- Missing/expired session returns to sign-in.
- Missing, revoked, suspended, foreign-branch, or forged Principal grant exposes no leadership page.
- Other roles never receive `leadership.read` implicitly.
- A multi-role account sees a distinct workspace choice; the selected role does not widen the underlying branch grant.
- Unavailable operational projections render an honest unavailable state without zero totals or dead actions.

Verification requires fixed-capability unit checks, real PostgreSQL grant/revocation/cross-branch/administrator-denial checks, migration compatibility, and desktop/mobile Playwright entry, role choice, revocation, keyboard, and screenshot comparison against the approved Principal pack. Human acceptance remains separate.

## Planned owner slices

LDR-02 owns the Attendance due-register read projection and exact metric definition. LDR-03 owns session evidence freshness. LDR-04 through LDR-06 require the approved Coordination write owner. No later approval or sensitive-record authority is inferred from this foundation.

## LEA-16 — Published timetable exception oversight

The independently releasable LEA-16 slice is a read-only projection of facts already owned by Timetable and Attendance. A live Principal receives `timetable.read_leadership`; this grants no Timetable draft/publication write, cover assignment, Attendance mutation, Teacher absence reason, pupil mark, or staff-performance inference. Every read rechecks the account token, active Institution/Branch and exact Principal membership, plus release, entitlement and branch activation for `timetable`, `academic_core`, `staff_core`, and `attendance`.

`leadershipTimetableOverview(actor, organizationId, schoolId, {cursor?,limit?})` selects the one current effective immutable publication on the branch-local date. It reports the publication/reconciliation identity and current persisted occurrence outcomes. Only `BLOCKED_MANUAL_CONFLICT`, `BLOCKED_DOMAIN_RULE`, and `FAILED_TECHNICAL` occurrences enter the bounded exception list. Ordering is `(local_date, starts_at, id)`; the UUID cursor is re-resolved inside the same branch/publication/exception predicate before it may advance the query. Offering and dated assignment joins stay organization/branch scoped. A manual-session evidence link is returned only when the Attendance-owned overlap matches the exact class or current Teacher; the target independently reauthorizes and withholds roster and marks.

The query runs in one repeatable-read transaction and performs no write or mutation lock. It reuses `vs_academics_timetable_revision`, `vs_academics_generation_checkpoint`, `vs_academics_lesson_occurrence`, scoped Offering/Teacher assignment reads, and the existing Attendance conflict evidence. No table, migration, receipt, or browser-supplied authority is added. Existing occurrence/source uniqueness and reconciliation serialization remain authoritative.

The full approved workflow remains partial. Current owners provide trusted reconciliation conflicts and safe evidence, but do not provide a general Teacher-absence/uncovered-class source or delegated cover/change command. Those actions remain blocked on the separately prepared TT-07/TEA-23 authority decisions and must not appear as working controls.

## LDR-02 / LEA-05, LEA-06 and LEA-08 design delta

Attendance owns `register-coverage.v1`; Leadership only presents its browser-safe DTO. The Principal capability is `attendance.read_leadership`, granted only by the explicit `PRINCIPAL` branch role. It is narrower than `attendance.read_school`: it permits the exact session-level completeness projection below and does not permit roster/pupil marks, absence explanations, correction history, exports, schedule/open/submit/correct/cancel, or administrator routes. Every read rechecks the live Principal role, account token version, Organization/School state, Attendance release, institution entitlement, branch activation and Attendance dependencies.

The metric reads one school-local date in a PostgreSQL `REPEATABLE READ` snapshot. Default is current school date; an explicit future date is rejected. The named first-release due policy is `SESSION_END_NO_GRACE`: a non-cancelled session is due when `ends_at <= server asOf`. `scheduled` is every non-cancelled session on the date; `due` is the due subset; `received` is due and `SUBMITTED`; `awaiting` is due and `SCHEDULED` or `OPEN`; `notDue` is non-cancelled with `ends_at > asOf`; `cancelled` is retained separately. The invariant is `received + awaiting = due`. An early submission whose scheduled end is later remains `notDue`, as required by the approved metric dictionary. No missing register is counted as an absent pupil, and no percentage is shown for an empty denominator.

`getLeadershipCoverage(actor, organizationId, schoolId, {date?,classId?,status?,teacherId?,sort?,order?,cursor?,limit?})` returns `{asOf,schoolDate,timezone,definitionVersion,duePolicy,counts,query,filters,awaiting:{items,total,nextCursor}}`. Awaiting items expose only session ID/version, class, subject, current dated expected-teacher display name, scheduled times, due instant and `SCHEDULED|OPEN`. They contain no pupil/roster/mark, private staff fact, explanation or follow-up. Class, session-state and responsible-Teacher filters are exact server-side predicates over the permitted branch/date result set and default to no selection. Filter options come only from that same authorized awaiting set. Sorting is `due|class` and `asc|desc`: due order uses `(ends_at,id)` and class order uses `(section_name,ends_at,id)`. The opaque cursor binds the complete filter/sort signature and cannot be replayed under another query. Pages default to 25 and max at 50; the browser never sorts a loaded page. The scoped count and list predicates are `(organization_id,school_id,school_date)` plus status/end cutoff; the existing `vs_attendance_session_school_day_idx` provides the scope/date access path, and sorting is bounded to one branch-day. Session→Offering→Section/Subject and Assignment→Teacher→Employee→Person joins retain both scope keys. If exactly one currently eligible dated Teacher assignment cannot be established, the display name and Teacher filter identity are unavailable rather than guessed.

No table, migration, lock or write is introduced. A failed/unauthorized source returns no totals. The home shows an explicit unavailable state rather than zero. The detail action belongs to LDR-03; LDR-02 does not expose a dead View action or reuse the administrator session route. Verification covers exact denominator arithmetic, early/future/cancelled states, query-bound keyset pagination, full-result-set class/status/Teacher filters, deterministic due/class sort, Back/Forward URL state, foreign/revoked/module denial, sensitive-field exclusion, current-source desktop/mobile navigation, no-due and populated screenshots, and the scoped PostgreSQL plan. Human review, native accessibility, font portability and TEN-03 remain separate gates.

## LDR-03 / LEA-08 exact source evidence

`getLeadershipSessionEvidence(actor, organizationId, schoolId, sessionId)` is an Attendance-owned, read-only query behind the same `attendance.read_leadership` gate as coverage. It re-establishes verified database context and rechecks the live Principal membership, account token version, active Organization/School, released module, institution entitlement, branch activation and dependencies on every call. A browser session ID is only a candidate: the scoped Attendance query and all Offering, Section, Subject and dated Teacher joins retain `(organization_id, school_id)`. Foreign, revoked or unavailable sources return no detail.

The safe DTO contains session ID/version, school date/timezone, scheduled start/end, Section, Subject, current dated expected-teacher display name, current lifecycle state, owner-maintained state-update time when known, server observation time, and derived evidence state `AWAITING|RECEIVED|CANCELLED|NOT_DUE`. It contains no roster, pupil mark, explanation, correction history, actor identity, export or mutation control. `SUBMITTED` becomes `RECEIVED` even if the register was awaiting on the previous page; `SCHEDULED|OPEN` is awaiting only after the scheduled end; cancelled and not-due states remain explicit. The detail page re-reads rather than trusting list state and preserves a date-qualified return path.

AttendanceSession gains nullable `state_updated_at timestamptz(3)` through a forward migration. Attendance lifecycle and timetable reconciliation writers set it atomically with the state/version change. Existing lifecycle timestamps and trustworthy schedule command receipts are backfilled; legacy scheduled rows without trustworthy source evidence remain null and display “not recorded” rather than an invented value. The detail lookup is by the existing scoped unique key and adds no index. Reads take no write locks. Verification covers fresh-state transition, foreign/revoked denial, source-field exclusion, populated/current screenshots, mobile composition and keyboard focus. The subsequent bounded-control slice completes LEA-08 with the approved class/status/Teacher filters and stable due/class sorting; LDR-03 itself remains the source-evidence checkpoint.

## LEA-02 branch-context isolation delta

Access remains the sole owner of the authorized destination list and context switch. A browser-supplied school ID is only a candidate: the switch command rechecks the live account, membership, exact `PRINCIPAL` grant and active destination before changing the account-bound selected-school cookie. The existing staged exit flow requires the leader to review unfinished work before confirmation. Current Leadership pages contain no editable durable draft or unresolved write command; this slice does not invent draft persistence or a browser authority flag.

Successful confirmation performs `location.replace('/leadership')`. This full document navigation deliberately destroys the old branch page, route filters and React Server Component state. The destination Leadership home and every owner projection independently reauthorize and reload the selected branch. The existing `pageshow` and `BroadcastChannel` guards reload back-forward-cache and cross-tab views after the account context changes, so a late response owned by the previous document cannot replace the destination DOM. A manually reused source ID remains only an input candidate and fails the destination branch's scoped owner query.

No table, migration, business write, lock or new transaction is introduced. The switch reuses the Access transaction and session-context behavior already verified by LDR-01; subsequent Leadership and Attendance reads take no write locks. Verification uses two explicitly granted branches with distinct real Attendance records to prove destination-only data, cleared class/status/sort URL state, destination recalculation, and denial of a prior-branch session deep link. Native accessibility, font portability, human review and TEN-03 remain separate gates.

## LEA-04 live-access change delta

Every Leadership layout request rechecks the exact Principal grant. Every Attendance coverage or source request separately rechecks its owner capability, released module, institution entitlement, branch activation and scoped resource identity. If Attendance becomes unavailable while a source page is open, the page retains no prior DTO and renders the generic unavailable state. The owner record is not deleted; restoring the module permits a fresh read of the same scoped source. If the Principal grant is removed, the Leadership layout exposes no child content and the existing role-aware redirect selects another currently permitted workspace. Reusing the former Leadership URL repeats the same server checks and cannot override the redirect.

This is a read-only first-release subset. Principal has no write command, unknown-outcome reference or command receipt, so the approved receipt/retry clause cannot yet be exercised without inventing authority. It remains an explicit dependency of the first future Principal write workflow. No source facts, denial audit table, schema, migration, lock or transaction is added. The Access and Attendance owner checks remain the enforcement boundary; hiding navigation is only presentation.

## LEA-46 — Own account and session security

The supported LEA-46 slice reuses the Access-owned account-session inventory and revocation boundary established by STW-44. The Principal route accepts no account ID: the hosting session supplies the account, token version and current opaque session ID. Access returns at most 20 active, unexpired sessions for that same global account and token version with only the safe browser category, start/expiry, version and current flag. A selected non-current session is reauthorized, locked and revoked by Access; exact repeat returns the prior semantic result without a second security event. Selecting the current session uses the separate NextAuth sign-out path, whose Access event revokes that exact server session before the protected context is cleared.

The application presents Review sessions → Revoke or sign out and retains the selected session only while moving Back/Continue. It performs no mutation until the final action. The existing Principal shell keeps account navigation and sign-out separate, and every later protected request validates the live session/account token. This adds no Principal role capability because own-account session control is global self-service; it grants no staff administration or access to another account's sessions.

No schema, migration, owner write, draft or new persistence is introduced. Existing Access unit and real-PostgreSQL evidence remains authoritative for account isolation, locking, repeat behavior, security-event uniqueness, expiry and token-version invalidation. Focused Principal browser evidence must prove an own non-current revoke, persistence after reload, current-browser sign-out, protected-route denial, keyboard focus, responsive layout and direct LEA-46 reference comparison. The full workflow remains partial: approved preference keys and a school-approved support configuration do not yet have owner contracts, so the page does not fabricate them.
