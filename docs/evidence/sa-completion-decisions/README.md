## SA-18 admission-date semantics

The approved field is `joined`, labelled **Admission date**, in SA-18 **School record** beside the branch-stable admission number. The live `Student` table `vs_students_student` has no such column: it stores branch scope, Person, admission number, status, version and `created_at`. The current registration UI/API accepts no date. `created_at` is a technical instant and cannot establish an admission date.

The other dates have different owners and meanings:

- `vs_students_enrollment.valid_from` is the first included day in one AcademicYear. A Student can have multiple yearly enrollments, and two current students have no enrollment in the development data.
- `vs_students_section_placement.valid_from` is dated section membership. A transfer changes only placement intervals from its effective date.
- attendance eligibility and frozen rosters use placement/session school dates. Reports use sessions/records and explicit report ranges. None currently reads an admission date.
- `Person.created_at`, `Student.created_at`, academic-year start, enrollment start and transfer effective date are therefore not accurate substitutes.

Read-only development evidence on 10 October 2026 found 6 Students, 4 yearly Enrollments, 4 Students with any enrollment, and 1 import source mapping. Student creation instants span 4–5 October 2026; enrollment starts span the same dates. No Student, import row, receipt or source map stores an independently verified admission date, so **zero existing records have an accurate source for automatic backfill**.

“Backfill” could mean four different operations: populate a currently missing value, permit an administrator to enter a historical date during new registration, correct an already stored date, or derive values for all legacy rows. Only the first two are needed to complete the approved field; correction and bulk derivation are separate behaviors. Changing an admission date must not rewrite Person identity, Enrollment/Placement intervals, attendance rosters/revisions or reports.

**Smallest product decision:** approve `Student.admitted_on` as the initial date the person entered this branch, independent of academic-year enrollment and later branch transfers. Require a valid historical or current school-local civil date for every new Student. Add it nullable only for the six legacy development records; show **Admission date unknown** until an authorized administrator explicitly fills the missing value from a trusted school record. Do not auto-derive it. Treat changing a non-null value as a later reasoned correction workflow.

Examples: a learner admitted to the branch on 2024-06-10 but enrolled in the 2026–27 year on 2026-06-01 stores `admitted_on=2024-06-10`; a learner transferred into this branch on 2026-09-15 stores that branch admission date even if a previous institution has an older date; a current legacy Student with only `created_at=2026-10-04` stays unknown. This option completes new registration honestly, preserves all historical joins, and gives a bounded manual legacy task. The owner accepted this branch-entry meaning and nullable-manual legacy rule. SA-COMP-12 implements it without deriving or rewriting history.
